| 收银排队与手动结账 | 扩展现有流程 | 结账是 2 秒自动完成，营业阶段玩家在收银台环节零参与 |
| PREP 备货阶段 | 节奏调整 | 上述手动操作塞进 75 秒营业时间会直接挤爆（测算详见 §2.9） |

**一句话核心增量**：让「货」第一次拥有物理生命——从街上的货车、门口的快递箱、后仓的存货，一路到货架上肉眼可见的那一盒；而玩家要亲手把它摆上去，并在收银台前亲手把钱收进来。

**分层模型（重要，供架构师与 Part B 对齐）**：

```
库存四态（按 SKU 计）
  inTransit ──货车到店──> inBox ──玩家开箱(1.5s)──> backroom ──玩家补货(4.0s)──> onShelf ──售出──> 消失
     ↑下单                  ↑门口实体箱              ↑后仓(抽象面板)            ↑货架格位(可见·可售)
```

- **只有 `onShelf` 的货会被顾客购买**，`backroom` / `inBox` / `inTransit` 均不可售。
- 顾客 `target` 仍是**品类**（`customers.js` 语义不变），另派生 `targetSku`（具体 SKU，供需求气泡与成交价使用）。

### 2.2 物流状态机（`src/sim/logistics.js`）

#### 2.2.1 状态枚举（**定稿，供 `street.js` 渲染货车与快递箱**）

```js
// 单个 delivery（一次下单 = 一辆货车）
DeliveryState = {
  ORDERED:    'ORDERED',     // 已下单，货车未发车（MORNING 阶段）
  IN_TRANSIT: 'IN_TRANSIT',  // 货车在途 —— street.js：货车从街角驶入
  ARRIVED:    'ARRIVED',     // 已到店并卸箱 —— street.js：门口堆叠 N 个快递箱，货车驶离
  DONE:       'DONE',        // 本单所有箱子已清空
}
// 单个 box（一辆货车卸下 N 个箱子，每箱 4 件同 SKU）
BoxState = {
  SEALED: 'SEALED',  // 密封 —— street.js：闭合纸箱 + 侧面 SKU 标签
  OPEN:   'OPEN',    // 已开箱待取 —— street.js：箱盖翻开；此时玩家按 F 取货
  EMPTY:  'EMPTY',   // 已取空 —— street.js：淡出移除
}
```

#### 2.2.2 完整流程（第一人称下）

| 步骤 | 阶段 | 玩家动作 | 耗时 | 状态迁移 |
|------|------|---------|------|---------|
| 1 | MORNING | 在进货面板按 SKU 下单（步进 4 = 一箱） | — | → `ORDERED` |
| 2 | **PREP** | 等货车（HUD 倒计时），可先走到门口待命 | **8s** | `ORDERED` → `IN_TRANSIT` → `ARRIVED` |
| 3 | **PREP** | 走到箱子 2.5u 内，**按住 F** 开箱 | **1.5s** | `SEALED` → `OPEN` |
| 4 | **PREP** | 对已开箱**按住 F** 取货 → 货物进后仓 | **0.6s** | `OPEN` → `EMPTY`，`inBox` → `backroom` |
| 5 | **PREP** | 走到对应品类货架 2.5u 内，**按住 F** 补货 | **4.0s/次**（一次补 4 件到一格） | `backroom` → `onShelf` |
| 6 | PREP 末 | 点「开门营业」；未处理的箱子留到营业中继续 | — | — |

- **一箱 = 一格**：`boxCapacity(4) = restockPerAction(4) = stackCapL1(4)`，一次开箱 → 一次取货 → 一次补货，**全程一件不多搬**。
- **批量化是操作强度的解药**：24 件货从「24 次点击」压缩成「6 次完整往返」（见 §2.10）。
- 开箱/取货/补货均**按住**生效，中途松开或走开即中断，已完成部分保留（补货按已补件数保留）。
- 门口箱子 > 8 个时，玩家经过门口速度 ×0.7（软惩罚，不阻断）。
- 事件「快递延迟」接入：`truckEta += 12s`。

#### 2.2.3 后仓（`backroom`）

- 抽象库存层，**不是 3D 房间**（与 B23「员工通道门 → 后台面板」共用同一入口，不建实体房间）。
- 后仓是**「找货 ❓」气泡的弹药库**：货架空了，但后仓有货 → 可立即补 1 件救场。
- 后仓无容量上限（现金与 SKU 库存上限已构成约束）。

### 2.3 货架陈列与商品状态

#### 2.3.1 货架状态枚举（**定稿，供 `needs.js`「找货」气泡与 `shelf.js` 陈列**）

> 这是 PM-2 在 §3.7 等待的第一个接口。采用 PM-2 的**原枚举名**，无需改 Part B 代码。

```js
ShelfState = {
  ON_SHELF:     'ON_SHELF',      // 该品类货架有陈列（onShelf > 0）—— 正常可售
  IN_BACKROOM:  'IN_BACKROOM',   // 货架空（onShelf === 0）但后仓有货 —— ★「找货 ❓」气泡的触发条件
  OUT_OF_STOCK: 'OUT_OF_STOCK',  // 货架空 且 后仓也无货 —— 真缺货，走原流失判定
}
```

**判定函数**（`logistics.js` 导出，按**品类**聚合，与 Part B 的 `CategoryId` 口径一致）：

```
shelfState(gs, cat):
  onShelf = Σ sku.onShelf  (sku.cat === cat)
  backroom = Σ sku.backroom
  onShelf > 0            → ON_SHELF
  backroom > 0           → IN_BACKROOM
  else                   → OUT_OF_STOCK
```

#### 2.3.2 货架格位模型

| 项 | 值 |
|---|---|
| 货架数 | 4（对应 4 品类，位置沿用 `SHELF_X`） |
| 每货架格位 | 9（3 层 × 3 列，与现有 3×3 商品盒视觉对齐） |
| 每格堆叠上限 | 货架 L1 **4** / L2 **6** / L3 **8** |
| 格位品类约束 | **格位只能放所属货架品类的 SKU，禁止跨品类混放**（规则清晰、可测试） |
| 同 SKU 多占格 | 允许（P2）：每多占 1 格，被选中权重 +15%，上限 ×1.5 |
| 初始状态 | **新开局货架全空**（严格对应用户需求「货架初始为空白货架」） |

#### 2.3.3 与 `shelf.js`（B16）的接口

PM-2 在 §3.5 写的 `shelfDisplay` 公式 `round(min(1, onShelf / cap) * 9)` 中的 **`cap` 请改为 `displayCap = 12`**：

```js
// shelf.js 可见商品实例数（按品类聚合）
visibleCount(cat) = Math.round(Math.min(1, onShelf(cat) / CONFIG.shelf.displayCap) * CONFIG.shelf.slotsPerShelf);
// 陈列 ≥12 件 → 9 格全显示；0 件 → 空架；backroom 有货但 onShelf=0 → 空架（不显示）
```

三个显示档位与货架状态枚举的对应关系：

| `ShelfState` | `shelf.js` 表现 |
|---|---|
| `ON_SHELF` | 显示 `visibleCount` 个商品实例（1–9） |
| `IN_BACKROOM` | **空架**（货在后台，货架上看不见）→ 视觉上提示「该补货了」 |
| `OUT_OF_STOCK` | 空架 + 灰色缺货标签 |

#### 2.3.4 陈列对销售的影响

- 顾客选品权重：`pref[cat] × seasonHeat[cat] × skuAppeal × displayWeight`，其中 `displayWeight = 1`（单格）/ `1.15`（2 格）/ `1.3`（3 格，上限 1.5）。
- **陈列不足惩罚（P1）**：全店陈列 SKU 数 < 4 时，所有顾客购买概率 ×0.85。
- 缺货替代：目标 SKU 无陈列 → 45% 概率接受同品类其他陈列 SKU；品类 `OUT_OF_STOCK` → 直接走现有 `leaveAngryChance 0.88`。

### 2.5 收银队列与手动结账

#### 2.5.1 队列模型（**定稿，消费 B02 的 `payTimeMult` / `parallelSlots`**）

- 顾客购买判定成功 → 从货架取货（`onShelf -= 1`，此时**尚未成交**）→ 走向收银台 → `QUEUED`。
- 队列容量 **5**，第 6 位不进队，平静离店（满意度 0，不触发声望惩罚）。
- 队首排队耐心 **20s**，第 2 位起 **14s**（与常规耐心并行倒计时，取先耗尽者）。
- **结账完成才计入收入**：现金 += SKU 售价，满意度 +1，触发常客剧情。
- 耐心归零 → 怒走：声望 **−1**，`today.lost +1`，**商品退回货架（库存不损失）**。

> **⚠️ 设计缺口与提案（PM-1，v0.6）—— 需裁决，见 A33**
>
> 手动结账（A23）引入一个 v1 不存在的结构性风险：**玩家不在柜台 = 零收入**。
> v1 的结账是 2s 自动完成，玩家全程 AFK 也能正常经营；现在若玩家在营业中去做别的事（处理 PREP 遗留的箱子、响应气泡、去街上），或单纯不在柜台，队列会持续积压 → 队首耐心 20s 耗尽 → **全员怒走、声望 −1/人、当日收入 0**。
>

>
> 这带来三个后果：
> 1. ~~**QA 基线不可测**：「0% 参与」= 收入 0 = 永不通关，**该档位在数学上不成立**~~ → ❌ **v0.6.1 已消解**：PM-2 的观测项 **#5（结账执行率固定 100%）** 把「0% 参与」这一档**从基线定义中排除**了（基线 = 玩家全程亲手结账），故 **QA 基线可测，R1 跑批不必等 A33**。本条不再是 A33 的成立理由。

> - 耗时 **5.0s**；满意度 **0**（不奖不罚，收入照常入账）；不再占用玩家队列位。
> - 🔒 **`selfServiceSatisfaction = 0` 为不可上调红线，与 `reputationGoal = 100` 同级（裁决 10）**：该值一旦被改为 +1，玩家全程 AFK 也能涨声望 → **v1 的 AFK 问题完整回归，A22/A23/A24 与收银员岗位同时失去意义**。

### 3.1 员工系统（`src/sim/staff.js`）

#### 3.1.1 岗位定义

| 岗位 ID | 名称 | 核心效果 | 与何系统耦合 |
|---------|------|---------|-------------|
| `cashier` | 收银员 | 结账耗时 2s → 1.2s；收银台并行位 1 → 2 | Part A 结账队列 |
| `guide` | 导购员 | 自动响应顾客需求气泡（见 §3.2） | §3.2 需求气泡 |
| `host` | 体验官 | 体验时长 −20%；体验后二次购买判定额外 ×1.1 | 现有体验区 |
| `stocker` | 仓管员 | "后台库存 → 上架"耗时 4s → 1.5s；每营业日自动补货 1 次 | Part A 物流状态机 |

#### 3.1.2 雇佣与成本

- **雇佣**：晨间决策阶段从候选人池中雇佣，一次性付**签约金**，此后按日付**日薪**。
- **解雇**：随时可解雇，需支付 **1 天日薪**作为遣散费。
- **排班**：每天晨间决定当日上班名单（可全休）。**只有上班当天才计日薪**——这是玩家控制现金流压力的主要阀门。

| 岗位 | 签约金 | 日薪 | 备注 |
|------|--------|------|------|
| 收银员 | 250 | 45 | 最便宜的吞吐解法 |
| 导购员 | 300 | 55 | 声望杠杆（见 §3.1.5 平衡意图） |
| 体验官 | 350 | 70 | 收益杠杆，需体验区 ≥2 级才有价值 |
| 仓管员 | 250 | 50 | 需配合 Part A 物流状态机才有价值 |

**员工数上限**：4 人（硬上限，无升级门槛）。

#### 3.1.3 技能星级

新员工生成时按权重抽取 1–3★，星级同时放大效果与日薪（**边际递减**：3★ 效果 ×1.5 但日薪 ×1.9）。

| 星级 | 效果倍率 | 日薪倍率 | 生成权重 |
|------|---------|---------|---------|
| 1★ | ×1.0 | ×1.0 | 0.55 |
| 2★ | ×1.25 | ×1.4 | 0.33 |
| 3★ | ×1.5 | ×1.9 | 0.12 |

#### 3.1.4 疲劳与离职

疲劳值 `fatigue ∈ [0, 100]`，整数。

| 事件 | 疲劳变化 |
|------|---------|
| 当日排班上班 | +25 |
| 当日排班休息 | −40 |

| 疲劳区间 | 效果 | 每日离职概率 |
|---------|------|-------------|
| ≤ 70 | 效率 ×1.0 | 2% |
| 71 – 90 | 效率 ×0.7 | 2% |
| > 90 | 效率 ×0.5 | 20% |

- **欠薪离职**：日结时现金不足以支付日薪 → 该员工当日离职概率 **35%**（先扣薪至 0，再判定）。
- **离职成本**：无赔偿金，但签约金沉没。离职后当日仍在岗完成营业（次日生效），避免"中途消失"的突兀感。
- **效率倍率**作用于岗位效果数值（如 2★ 导购员疲劳 85 → 响应间隔 `12 / (1.25 × 0.7) ≈ 13.7s`）。

#### 3.1.5 平衡意图（重要，供架构师与 QA 校验）

> 员工**不是赚钱工具，而是「用现金换声望 / 换容错」的杠杆**。

- 单人日薪 45–70，而原型早期日均净利仅 +50~+150 → 雇人即显著吃紧，构成真实取舍。
- 导购员是唯一直接买声望的岗位，故做三重削弱：响应间隔 12s（非 8s）、响应成功率 80%、仅"找货/投诉"两类气泡给 +1 满意度（其余只给耐心或概率加成）。

### 3.2 顾客需求气泡（`src/sim/needs.js`）

#### 3.2.1 设计定位

旧实现的顾客头顶 emoji 只表达**心情**（不可交互）。新增的**需求气泡**表达**可响应的求助信号**：气泡出现 → 玩家（或导购员）点击响应 → 改变该顾客的结果。

这是**轻干预框架内的操作**，不是强制操作：不响应只会让顾客按原有概率流失，不会直接判负。

#### 3.2.2 气泡类型表

| 气泡 | emoji | 触发条件 | 玩家响应动作 | 响应奖励 | 存活时长 | 超时后果 |
|------|-------|---------|-------------|---------|---------|---------|
| **找货** | ❓ | `shelfState(targetCat) === 'IN_BACKROOM'` —— **货架空 + 后仓有货**（Part A §2.3.1 定稿） | 从后仓补 1 件到该货架 | 满意度 **+1**，购买概率 ×1.3 | 8s | 转入原流失判定（现有 `leaveAngryChance` 0.88） |
| **投诉** | 😠 | 顾客耐心 < 25% | 赠送小样（成本 5 金币） | 耐心回满至 60%，满意度 0（本可 −1） | 5s | 耐心耗尽流失，满意度 −1 |
| **结账** | 💳 | 收银队列 ≥3 且队首等待 >6s | 玩家亲自开临时收银（耗时 1.5s，期间不可做其他响应） | 满意度 +1，队列 −1 | 6s | 队首耐心耗尽流失 |
| **讲解** | 💬 | 顾客在体验位外排队 >3s | 有空位则立即安排入座；无空位则安抚 | 耐心 +8s | 8s | 耐心继续正常扣减 |
| **推荐** | ⭐ | 浏览结束、购买判定失败、且预算充足 | 改 `target` 到有货的次优品类，购买判定**重掷一次** | 重掷成功则正常成交 | 5s | 转入流失判定 |

#### 3.2.3 生成与调度规则

- **扫描**：营业阶段每 0.5s 逻辑 tick 扫描一次在场顾客，按触发条件生成气泡。
- **同屏上限 3 个**，超出时按紧急度排序，低优先级气泡排队等待。
  **紧急度**：`投诉 > 结账 > 找货 > 讲解 > 推荐`
- **不重复**：同一顾客同一类型气泡响应后进入 **6s 冷却**，冷却期内不再弹出同类型。
- **玩家全局响应冷却 3s**（防止连点刷满意度）；员工无此冷却。

#### 3.2.4 与员工/第一人称的耦合（关键设计 · 见裁决 4）

| 响应主体 | 约束 |
|---------|------|
| **玩家（等距俯瞰模式）** | 直接点击气泡即可响应，无距离限制 |
| **玩家（第一人称模式）** | **必须走到顾客 2.5 世界单位内**才可响应；HUD 对超距气泡显示距离提示 —— **不可裁剪，等同 P0** |
| **导购员（NPC）** | 每 12s 自动处理 1 个气泡，成功率 80%；优先处理紧急度最高的 |

> **这条距离约束是第一人称视角的核心价值锚点**：它把"在店里跑动"从观光变成有收益的操作。若砍掉此约束，第一人称将退回纯观光功能。

#### 3.2.5 优先级

| 级别 | 内容 |
|------|------|
| **P0** | 5 类气泡与触发表、玩家点击响应、全局 3s 冷却、优先级排序与同屏上限 3、**第一人称 2.5 单位距离约束（不可裁剪）** |
| **P1** | 导购员自动响应、气泡冷却与排队等待 |
| **P2** | 气泡美术差分（不同紧急度不同颜色/抖动）、响音效反馈 |

### 3.8 待确认问题（Part B）

1. **员工 3D 可见性**：员工是否作为可见小人在店内走动？—— **建议是**（增强临场感，且让"导购员在响应气泡"可被感知），但会增加角色渲染与寻路成本。

#### 5.1.1 Q2 复核依据（PM-2 源码验证 —— ✅ **裁决 9 已采纳为本节结论**）

> **注：本节为 PM-2 提交的源码复核意见。经 team-lead 亲自复核源码确认后已由裁决 9 采纳，现为执行口径依据（不再是留痕）。**

**原 Q2 的前提「营业 75→105s 会把通关天数从 18–25 天延到 22–28 天」经源码复核不成立。**

`src/sim/day.js:118–122`：

```js
const count = dailyFootfall(gs);                                  // ← 每日客流总数
const horizon = CONFIG.openDuration - CONFIG.customer.browseMax * 2;
for (let i = 0; i < count; i += 1) {
  const t = ((i + rng.next()) / count) * horizon;                 // ← openDuration 只决定「怎么摊」
```

- `dailyFootfall(gs)`（`economy.js:87`）的入参只有 `gs.reputation` / 事件 / 活动周 / 传说加成，**与 `openDuration` 完全无关**——客流是**按天的固定总数**，不是按秒的速率。
- `openDuration` 只影响 `horizon`，即把这 `count` 个顾客**摊在多长的时间窗里**。

因此延长营业时长**不会减少也不会增加每日客流**，每日声望增益基本不变 → 通关天数不应发生 22–28 天这样的位移。

**二阶效应方向一致地指向「持平或更快」，而非更慢**：

| 效应 | 方向 |
|------|------|
| 顾客在更长窗口里摊得更稀 → 体验位/收银台争用减少 | 怒流失 ↓ → 声望 ↑（**更快**） |
| 晚进店的顾客有更充足时间走完流程 | 成交 ↑（**更快**） |
| `stepSession` 在 `clock ≥ openDuration` 后仍继续步进在场顾客直至散尽 | 75s 窗口本身也**不会截断**顾客流程（**无差异**） |
